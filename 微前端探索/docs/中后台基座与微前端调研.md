## 1. 这类项目叫什么

同一个项目通常会落在多个交叉类别里，不存在唯一正式名称。

| 中文叫法 | 英文关键词 | 核心职责 | 典型代表 |
| --- | --- | --- | --- |
| 中后台前端框架 | Admin Framework | 布局、路由、权限、菜单、页签、主题、数据层 | Vben Admin、Soybean Admin |
| 中后台基座 / 前端基座 | Admin Shell / Application Shell | 承载业务应用的通用外壳与公共能力 | Vben Admin、企业统一门户 |
| 微前端基座 | Micro-frontend Host / Shell | 子应用注册、加载、沙箱、通信、路由主权 | qiankun、wujie、Garfish |
| 企业级后台模板 | Admin Boilerplate / Starter | 可直接复制作为新项目起点 | vue-element-admin、RuoYi-Vue3 |
| 统一门户 | Unified Portal | 多系统统一入口、单点登录、菜单聚合 | icestark 方案、企业自建门户 |
| Monorepo 前端架构 | Monorepo Admin Starter | 框架包 + 示例应用 + CLI 一体维护 | Vben Admin v5、本项目 |

**本项目的准确定位：**

> 基于 Vue 3 的微前端中后台框架（Monorepo + npm 包 + 基座/子应用）。

它同时具备两层能力：

- 应用框架层：`@admin/core`、`@admin/ui`、`@admin/auth`
- 微前端运行时层：`@admin/micro`、`@admin/bridge`

与“后台模板”的区别是：模板复制代码，框架发布 npm 包。
与“低代码平台”没有直接关系。

### 3.1 微前端运行时基座

| Soybean Admin | Vue 3 + Naive UI | 设计感强，主题系统完善 |

### 3.3 组合型：应用框架 + 微前端基座

这是最接近本项目的形态。

| 形态 | 说明 |
| --- | --- |
| qiankun + vue-element-admin | 经典“基座 + 子应用”改造方案，如 Gitee 上的 qiankun-TMVC |
| icestark Framework Application | 基座统一管理公共 Header/Sidebar，子应用独立开发部署 |
| Garfish 主应用 + 子应用 | 字节系主应用模型，支持多框架混合 |
| Vben Admin + qiankun | Vben 作为宿主壳，qiankun 负责装载业务子应用 |

**注意：**“基座”是一个架构角色，不是一个标准项目名。很多名为“XX 基座”的仓库只是演示工程，需要看它是否真正解决了路由主权、沙箱、权限、通信和部署问题。

## 4. Vben Admin 与 qiankun 的架构差异

### 4.1 一句话结论

**Vben Admin 是“中后台应用框架”，qiankun 是“微前端运行时基座”。两者不在同一层，不是替代关系，而是可以组合的关系。**

- Vben 解决：一个后台应用应该有哪些布局、权限、路由、主题、国际化、页面能力。
- qiankun 解决：多个独立应用如何装进一个宿主，如何加载、挂载、隔离、通信、卸载。

### 4.2 定位对比

| 维度 | Vben Admin | qiankun |
| --- | --- | --- |
| 本质 | 中后台应用框架 / 模板 | 微前端运行时库 |
| 交付形态 | Monorepo 工程 + `apps/*` + `packages/*` | npm 包 + 主应用/子应用接入约定 |
| 核心目标 | 快速构建一个后台应用 | 组合多个独立前端应用 |
| 业务页面 | 内置大量后台页面与示例 | 不提供业务页面 |
| 布局/菜单/页签 | 内置 | 不提供 |
| 权限体系 | 内置 | 不提供，需要宿主自己实现 |
| 主题/国际化 | 内置 | 不提供 |
| 沙箱隔离 | 不需要（单应用） | JS 沙箱、样式隔离、HTML Entry |
| 技术栈 | Vue 3 生态，支持多 UI 库 | 框架无关，React/Vue/Angular 都可 |
| 部署单位 | 每个 `app` 可独立构建部署 | 子应用天然独立部署 |
| 典型使用 | 新后台项目起步 | 老系统整合、统一门户、多团队并行 |

### 4.3 架构形态

```text
Vben Admin（单应用框架）
┌─────────────────────────────────────┐
│ apps/web-antd                       │
│  ├─ 布局 / 菜单 / 页签 / 权限 / 主题 │
│  ├─ 业务页面                        │
│  └─ packages/* 公共能力             │
└─────────────────────────────────────┘

qiankun（微前端基座）
┌─────────────────────────────────────┐
│ 主应用 Host                          │
│  ├─ 注册子应用                      │
│  ├─ 路由激活 / 沙箱 / 通信          │
│  └─ 挂载容器                        │
└──────────────┬──────────────────────┘
               │
     ┌─────────┴─────────┐
     ▼                   ▼
┌───────────┐       ┌───────────┐
│ 子应用 A  │       │ 子应用 B  │
└───────────┘       └───────────┘
```

组合后：

```text
Vben Admin 作为宿主/壳
└─ qiankun 负责装配多个业务子应用
```

### 4.4 关键机制差异

**路由主权**

- Vben：一个 Router，菜单和页面在同一应用内，路由天然统一。
- qiankun：主应用持有顶层 URL，子应用有自己的 Router，容易出现双 Router、深链刷新、子应用跳转覆盖等问题。

这是组合时最大的技术难点。

**隔离**

- Vben：单应用，不需要 JS/CSS 沙箱。
- qiankun：需要处理全局变量、样式污染、`document`/`window` 代理、子应用卸载清理。

**权限**

- Vben：菜单、路由、按钮权限是框架内建能力。
- qiankun：只负责“装载”，权限必须由主应用或子应用自己实现。

**部署**

- Vben：Monorepo 内多个 `apps` 可以独立构建，但本质仍是多个后台应用。
- qiankun：子应用可以完全独立仓库、独立发布、独立回滚。

**通信**

- Vben：Pinia、Provide/Inject、组件 Props。
- qiankun：主应用通过 props 传参，或使用全局状态/事件总线；跨应用通信需要自己定协议。

### 4.5 能否组合

可以，常见两种方式：

**方式 A：Vben 作为主应用，qiankun 装载子应用**

- Vben 负责布局、菜单、权限、主题。
- qiankun 负责子应用加载与沙箱。
- 需要改造 Vben 的路由和内容区，增加子应用容器与路由上报。

**方式 B：Vben 作为 qiankun 子应用**

- 需要导出 qiankun 生命周期（`bootstrap/mount/unmount`）。
- 需要处理 `base` 路由、静态资源路径、独立运行与挂载运行两种模式。
- Vben 自带的布局通常要关闭或裁剪，避免与宿主布局重复。

### 4.6 选型建议

| 场景 | 建议 |
| --- | --- |
| 只需要一个后台应用 | Vben Admin 这类应用框架 |
| 多个独立团队/老系统整合 | qiankun 这类微前端基座 |
| 既要后台壳，又要装多个子应用 | 应用框架 + 微前端基座组合 |
| 想学习微前端原理 | 先 single-spa，再 qiankun/wujie |
| 想学习后台工程化 | Vben Admin 的目录与包拆分 |

### 4.7 常见误区

- 误区一：把 Vben 当微前端框架。它默认不提供子应用装载与沙箱。
- 误区二：把 qiankun 当后台框架。它不提供布局、菜单、权限、主题。
- 误区三：只看 Star 数，不看维护活跃度与文档。
- 误区四：认为“基座”一定要用微前端。单应用也可以用应用壳，只是没有运行时隔离。

## 5. 对当前项目的映射

| 当前项目 | 对应角色 | 可对照对象 |
| --- | --- | --- |
| `@admin/core` | 应用框架核心：路由、权限、菜单、页签、数据层 | Vben Admin 的 `@vben/*` 核心包 |
| `@admin/ui` | 布局与视觉层：Layout、登录页、主题、水印、通知 | Vben Admin 的 layouts / UI 应用 |
| `@admin/auth` | 登录态、权限指令、`useAuth` | Vben 的 access 模块 |
| `@admin/micro` | 微前端运行时：适配器、宿主、健康检查 | qiankun / wujie 的运行时 |
| `@admin/bridge` | 基座与子应用通信协议 | qiankun props / 全局状态 |
| `examples/playground` | 基座宿主 | qiankun 主应用 |
| `examples/remote-order` | 子应用 | qiankun 子应用 |

本项目的关键差异点：

- 路由即清单：菜单、面包屑、页签、keep-alive、权限都从 `RouteMeta` 派生
- 顶层 catch-all + 子应用上报 + `initialPath` 恢复，解决双 Router 冲突
- 适配器可替换：wujie 默认，iframe 降级
- 子应用健康检查与来源白名单
- 框架包化：可通过 npm 包引入其他项目

## 6. 建议的研究路线

1. **明确目标**：你是要“做一个后台”，还是“整合多个应用”，还是“做可复用框架”。
2. **读架构文档**：先看目录结构、包职责、启动流程，不要一上来读业务页面。
3. **跑 Demo**：重点体验登录、权限、菜单、页签、主题、子应用挂载。
4. **画三张图**：路由时序图、权限流程图、子应用挂载/卸载时序图。
5. **对照本项目**：用第 5 节的映射表逐项比较。
6. **做一个 Spike**：只验证一个能力，例如“子应用深链刷新”或“权限版本变化重建路由”。
7. **产出决策记录**：记录为什么选/不选某个方案，避免只收藏不消化。

## 7. 评估清单

### 工程与交付

- [ ] 是模板还是可复用框架
- [ ] 是否 Monorepo，包边界是否清晰
- [ ] 是否支持 npm 包引入
- [ ] 构建、类型检查、测试、CI 是否齐全
- [ ] 版本一致性与依赖方向是否有约束

### 路由与权限

- [ ] 菜单是否由路由派生
- [ ] 权限码模型是否扁平、是否支持通配
- [ ] 路由守卫是否区分 403/404/500
- [ ] 权限版本变化是否自动重建路由
- [ ] 是否支持按钮级权限

### 微前端

- [ ] 路由主权在基座还是子应用
- [ ] 子应用能否独立运行
- [ ] 是否有沙箱与样式隔离
- [ ] 是否有健康检查、降级与来源白名单
- [ ] 通信协议是否类型化、可序列化

### 主题与体验

- [ ] 是否 token 化，是否支持亮暗主题
- [ ] 是否支持主色自定义与持久化
- [ ] 是否有页签、面包屑、命令面板
- [ ] 是否有水印、离线提示、会话过期提示
- [ ] 是否支持窄屏与减少动效

### 数据与运维

- [ ] 请求层是否支持超时、取消、重试、去重
- [ ] 列表是否支持查询、分页、排序、URL 同步
- [ ] 是否有字典、列配置、导出、上传
- [ ] 是否有错误上报、版本更新提示、通知中心
