# 02 微前端形态与路由整合

> 探索阶段中间产物。目标是判断「微前端用什么形态、路由怎么并进基座」。

## 0. 先问一句：真的需要微前端吗？

微前端解决的是**组织问题**，不是代码组织问题：

```
触发微前端的事实（有任意一条才考虑）
+------------------------------------------+
| 1. 子应用要独立部署 / 独立发布节奏        |
| 2. 不同团队各自维护，代码库不共享         |
| 3. 存量系统（Vue2/jQuery/React）必须共存  |
| 4. 子应用需要独立域名 / 独立权限体系      |
+------------------------------------------+

如果只是「代码太多想拆分」：
  monorepo + 内部 npm 包 / 动态 import 就够了，
  引入微前端只会多一层运行时故障点。
```

本项目的定位是**框架自带可选的微前端能力**，所以结论不是「用不用」，而是「默认不用、需要时一行配置」。

## 1. 五种形态对比

| 维度 | qiankun | wujie（无界） | micro-app | Module Federation 2.0 | 纯 npm 包基座（无运行时装载） |
| --- | --- | --- | --- | --- | --- |
| 隔离原理 | Single-SPA + Proxy 沙箱 | WebComponent 容器 + iframe 沙箱 | CustomElement + 沙箱 + scoped CSS | 构建期共享模块，无应用沙箱 | 无隔离（同进程） |
| JS 隔离强度 | 中 | 高（iframe 原生） | 中高 | 无 | 无 |
| CSS 隔离强度 | 中（scoped/experimental） | 高（Shadow DOM） | 中高（scoped） | 无 | 无 |
| Vite / ESM 支持 | 差（需 vite-plugin-qiankun） | 好（原生支持） | 较好 | 好（@module-federation/enhanced） | 好 |
| 子应用改造量 | 高（生命周期、publicPath、路由） | 低（普通 Vue3 应用即可） | 低 | 中（需配置 exposes/shared） | 无 |
| 路由整合 | activeRule + 容器 | sync / 独立路由 | baseroute | 原生 Vue Router 合并 | 原生 |
| 弹层组件（Dialog/Popper） | 易逃逸出隔离区，样式错乱 | 正常（在 iframe document 内） | 一般 | 正常 | 正常 |
| 保活（keep-alive） | 支持 | 支持（alive） | 支持 | 需自行实现 | 原生 keep-alive |
| 跨技术栈 | 支持（需改造） | 支持（最彻底） | 支持 | 主要同栈 | 不支持 |
| 调试体验 | 中 | 中（iframe 内调试） | 中 | 好（源码级） | 最好 |
| 生态成熟度 | 高（蚂蚁，老牌） | 中（腾讯，社区较小） | 中高（京东） | 高且上升 | - |
| 对基座侵入 | 中 | 低 | 中 | 高（构建配置） | 无 |

### 关键判断

1. **qiankun 可以排除**：Vite + Vue3 是既定技术栈，qiankun 对 ESM 的支持要靠社区插件，且 UI 库弹层在 Proxy 沙箱下容易跑到宿主体内导致样式错乱。管理后台大量使用 Dialog/Select/Dropdown，这个坑会反复出现。
2. **wujie 是默认适配器的合理选择**：iframe 天然解决 JS 隔离与弹层问题；子应用几乎零改造；CSS 通过 Shadow DOM 隔离，同时 CSS 变量可继承，主题令牌能穿透。
3. **micro-app 是备选**：接入也轻，但生态与文档略逊，且 scoped CSS 对第三方 UI 库的覆盖不如 iframe 彻底。
4. **Module Federation 不是同类方案**：它解决「共享模块」，不解决「应用隔离 + 路由整合」。适合同栈、同构建体系、想共享设计系统与依赖的场景，且更适合作为「组件级联邦」而非「整站子应用」。
5. **纯 npm 包基座是基线**：微前端是它的可选扩展，而不是反过来。

### 推荐结论

```
默认：npm 包基座（core/ui/auth）
可选：@admin/micro + wujie 适配器（按需安装，不进 core）
预留：adapter 接口 + MF 适配器（同栈共享场景，P3）
降级：iframe 直挂（任意存量系统，零依赖）
```

## 2. 路由整合的三种模式

这是整个方案里最容易翻车的地方。基座必须**保有 URL 主权**，否则刷新 404、页签错乱、面包屑失效。

### 模式 A：委派路由（推荐默认）

基座声明路由，子应用被挂载在容器里：

```
浏览器 URL:  /system/user/list
                 |        |
                 |        +-- 子应用内部路由（system 应用自己的 router）
                 +----------- 基座路由：/system/*  -> <MicroAppHost name="system"/>

基座路由表：
  { path: '/system/:pathMatch(.*)*', component: MicroAppHost,
    meta: { micro: 'system', title: '系统管理', permission: 'system:view' } }
```

- 基座负责：登录态、权限、页签、面包屑、404、加载态、错误边界。
- 子应用负责：自身页面与内部导航，router base 固定为 `/system`。
- 子应用路由变化通过 props 回调上报给基座，用于更新页签标题与面包屑。
- 优点：URL 连续、可分享、刷新可用；基座体验统一。
- 代价：子应用的深层路由对基座不可见，除非提供 route manifest 或运行时上报。

### 模式 B：自治路由（存量迁移用）

```
浏览器 URL:  /legacy/**   -> 整个前缀交给子应用
基座只做「壳」：布局 + 登录态 + 一个全屏容器
```

- 适合 jQuery / Vue2 老系统，子应用自己管路由，基座不介入。
- 代价：页签、面包屑、权限按钮都无法统一，属于过渡态。

### 模式 C：原生合并（Module Federation / npm 远程组件）

```
子应用 export routes 或页面组件
        |
        v
基座 router.addRoute() 直接合并，无容器、无沙箱
```

- 体验最好（真正的单应用），同栈首选。
- 前提：构建期联邦或包依赖，版本必须对齐；不适合异构/独立部署。
- 适合「共享页面/组件」而不是「独立应用」。

### 选择建议

```
需要独立部署 + 异构/存量  -> 模式 A（wujie）+ 模式 B 兜底
同栈同构建、只共享页面    -> 模式 C（MF）
只想复用一个表格组件      -> 直接发 npm 包，别上微前端
```

## 3. 隔离与通信的具体设计点

### 3.1 样式

```
基座 :root { --admin-color-primary: #1677ff; --admin-radius: 8px; }
        |
        | CSS 自定义属性可穿透 Shadow DOM
        v
子应用 :shadow-root 内使用 var(--admin-color-primary)
```

- 主题令牌走 CSS 变量，是唯一推荐的跨应用样式契约。
- 禁子应用覆盖 `:root` / `body`；禁全局 reset。
- 子应用 UI 库样式必须随子应用自身注入（wujie 会把子应用样式放进 shadow root）。

### 3.2 运行时

- 每个子应用独立 Vue 实例、独立 Pinia、独立 router。
- 共享能力（登录态、主题、权限码、i18n）通过 **props 快照 + 事件总线** 传递，不共享响应式对象。
- 禁止把基座的 `router` 实例直接交给子应用（会互相污染）。

### 3.3 通信契约

```
基座 -> 子应用：props（初始化时）+ bus.emit('theme:change' | 'auth:change' | 'route:change')
子应用 -> 基座：bus.emit('app:route-change' | 'app:title' | 'app:error' | 'app:request-auth')
请求-响应：bridge.request('auth:get-token') -> Promise<string>
```

统一收敛到 `@admin/bridge`，事件名与 payload 有类型定义；wujie 的 bus 只是其中一个 transport 实现。

### 3.4 失败与降级

| 故障 | 处理 |
| --- | --- |
| 子应用 JS 加载失败 | 容器内错误态 + 重试按钮，不白屏 |
| 子应用路由 404 | 基座兜底页，保留布局 |
| 子应用崩溃 | 错误边界捕获，卸载并提示 |
| 浏览器不支持 Shadow DOM | wujie `degrade` 降级为 iframe |
| 子应用长时间未 ready | 超时（默认 10s）提示，允许返回 |

### 3.5 登录态与鉴权

- 同域优先：Cookie（HttpOnly）+ 基座统一登录页，子应用不碰 token。
- 跨域时：基座通过 props 传短期 access token，子应用存内存，请求走 bridge 代理或带 header。
- 子应用权限：基座下发「当前用户权限码快照」，子应用本地判断；后端仍强制校验。

## 4. 结论摘要

1. 微前端做成 `@admin/micro` 可选包，core 只依赖 `MicroAppAdapter` 接口。
2. 默认适配器选 wujie（Vue3 + Vite + UI 库弹层友好 + 隔离彻底）。
3. 路由默认「模式 A 委派」，保留模式 B 作为存量迁移出口，模式 C 留给 MF 场景。
4. 跨应用契约只有三样：CSS 变量（主题）、props 快照（上下文）、typed bus（事件）。
5. 任何子应用都必须能在「独立运行」和「被基座挂载」两种模式下工作，这是接入成本的底线。
