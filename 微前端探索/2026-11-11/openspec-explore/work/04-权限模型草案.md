# 04 权限模型草案

> 探索阶段中间产物。目标是确定「前端消费什么、后端返回什么、边界在哪」。

## 1. 模型选择

```
用户 --N:N--> 角色 --N:N--> 权限点
  |                             |
  +-------- 租户（可选，v1 不做）+

权限点 = "资源:动作"，例如：
  system:user:list
  system:user:create
  order:refund:approve
```

三种候选模型：

| 模型 | 前端需要的数据 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 纯角色（RBAC，前端映射权限） | roles | 后端简单 | 角色→权限映射要在前端维护一份，双份真相，必然漂移 |
| 角色 + 扁平权限码（推荐） | roles + permissions | 前端只做匹配，后端可任意演进角色 | 权限码数量可能多，需要约定命名 |
| ABAC / 策略引擎 | 策略或查询接口 | 最灵活 | 前端无法离线判断，每次都请求，管理后台过度设计 |

**推荐：角色 + 扁平权限码。** 角色只用于展示与粗粒度判断，权限码用于菜单/路由/按钮。

## 2. 后端契约

### 2.1 获取当前用户

```
GET /api/auth/me

200 {
  "user": { "id": "u_1", "name": "张三", "avatar": "https://..." },
  "roles": ["ops_admin"],
  "permissions": [
    "system:user:list",
    "system:user:create",
    "order:view"
  ],
  "permissionsVersion": "2026-11-11T10:00:00Z"
}
```

约定：
- `permissions` 是**当前用户的有效权限码全集**，由后端计算，前端不做角色展开。
- 超级管理员返回 `["*"]`，前端匹配时 `*` 命中一切。
- `permissionsVersion` 用于角色变更后让前端判断是否需要重新拉取；无此字段则每次刷新页面重拉。
- 无权限时返回空数组，不要返回 `null`。

### 2.2 登录 / 登出 / 刷新

```
POST /api/auth/login   -> { accessToken?, refreshToken? } 或直接 Set-Cookie
POST /api/auth/logout
POST /api/auth/refresh -> { accessToken }
```

- 同域部署优先 HttpOnly Cookie，前端完全不碰 token。
- 跨域才使用 header token，由 `http` 层统一注入。
- 401 统一拦截：尝试 refresh 一次，失败则清空状态并跳登录（带 `redirect` 参数）。

### 2.3 可选：动态菜单

仅在「运营可配置菜单」场景需要：

```
GET /api/auth/menus

200 {
  "menus": [
    { "key": "system", "title": "系统管理", "icon": "Setting", "order": 90,
      "children": [
        { "key": "system.user", "title": "用户管理", "component": "system/user", "permission": "system:user:list" }
      ] }
  ]
}
```

约束：
- `component` 必须是**字符串白名单键**，映射到前端 `import()` 表，绝不允许后端下发 URL 或任意路径（安全 + 打包约束）。
- 动态菜单与静态路由必须能合并，不能二选一（否则代码里定义的路由就白写了）。
- 建议 v1 不做，先把静态模式打磨好。

## 3. 三种消费方式

### 3.1 路由级（菜单自动派生）

```ts
{ path: 'user', meta: { title: '用户管理', permission: 'system:user:list' } }
```

守卫流程：

```
router.beforeEach
   |
   v
是否有登录态？ --否--> /login?redirect=当前地址
   |
  是
   v
是否已加载 me？ --否--> await auth.load()  (并发去重)
   |
   v
目标路由是否匹配权限？
   |            |
  否           是
   |            |
   v            v
 /403        放行 + 记录页签
```

要点：
- `auth.load()` 必须并发去重（多个守卫同时触发只发一次请求）。
- 未匹配到路由（404）与无权限（403）要区分，否则用户永远不知道自己错在哪。
- 刷新页面时先加载权限再 `addRoute`/过滤，避免「先 403 后恢复」。

### 3.2 按钮级

```vue
<!-- 指令 -->
<el-button v-perm="'system:user:create'" @click="create">新建</el-button>
<el-button v-perm.any="['a', 'b']">批量操作</el-button>

<!-- 组件（需要 else 分支时） -->
<Permission code="system:user:delete" :fallback="{ disabled: true }">
  <el-button type="danger">删除</el-button>
</Permission>

<!-- 逻辑 -->
<script setup>
const { can } = useAuth()
const canDelete = computed(() => can('system:user:delete'))
</script>
```

### 3.3 数据级（v1 不做，只留口子）

行级/字段级权限必须由后端返回数据时过滤或标记，前端只做展示。v1 不定义协议，但在 `auth` 中预留 `auth.scope` 字段，避免以后加字段破坏类型。

## 4. 权限码规范

```
<domain>:<resource>:<action>
  domain   业务域，如 system / order / report
  resource 资源，如 user / refund
  action   list | detail | create | update | delete | export | approve | assign

示例：
  system:user:list
  order:refund:approve
  report:dashboard:export
```

规则：
- 全小写，冒号分隔，不超过 3 段（超 3 段用连字符）。
- 通配符只支持两种：`*`（全部）和 `system:user:*`（资源下全部）。
- 权限码是**契约**，一旦发布不得重命名；废弃用新码替代并保留旧码一段时间。

前端声明方式（防拼写错误）：

```ts
export const P = {
  system: {
    user: {
      list: 'system:user:list',
      create: 'system:user:create',
    },
  },
} as const

v-perm="P.system.user.create"
```

## 5. 菜单与权限的关系

```
路由表（代码） + 权限码集合（后端）
        |
        v
   过滤后的路由树
        |
        +--> 侧边菜单
        +--> 面包屑
        +--> 页签标题
        +--> keep-alive 名单
```

一个来源，四处消费。禁止再提供独立的 `menu.config.ts`。

## 6. 边界与安全

| 事项 | 结论 |
| --- | --- |
| 前端权限能否作为安全边界 | **不能**。所有接口后端必须独立鉴权 |
| 按钮隐藏是否等于安全 | 不等于，只是减少误操作与信息暴露 |
| 权限码能否由前端角色展开 | 不能，避免双份映射 |
| 前端缓存权限多久 | 内存 + sessionStorage，带 `permissionsVersion` 校验 |
| 角色变更后 | 下一次接口 403 或版本不一致时刷新 me |
| 子应用权限 | 基座下发快照；子应用接口仍由后端校验 |

## 7. 典型边界情况

1. **用户直接输入无权限 URL** → 403 页面，保留布局，提供返回首页。
2. **有路由无菜单**（详情页） → `menu: false` + `activeMenu` 指定高亮项。
3. **父级有权限、子级全无权限** → 父级菜单隐藏。
4. **只有外链菜单** → `external` + 新窗口打开，不参与路由。
5. **权限加载失败** → 显示错误页 + 重试，不要静默放行，也不要死循环跳登录。
6. **多标签页同时登出** → 监听 storage 事件，统一清空并跳登录。
7. **子应用内 401** → 通过 bridge 通知基座，由基座统一处理，避免子应用各自跳登录。
8. **keep-alive 与权限回收** → 权限变化时清空缓存页签，防止越权查看历史数据。

## 8. 开放问题

- 是否需要「菜单配置化」（运营可调顺序/名称/可见性）？影响是否要做 P2 的动态菜单。
- 是否需要多租户（`tenantId`）与 SSO？影响 `me` 契约与登录流程。
- 是否需要按钮级权限的「禁用而非隐藏」策略？影响指令 API。
- 权限码是由后端统一定义，还是各业务域自治？影响命名治理。
