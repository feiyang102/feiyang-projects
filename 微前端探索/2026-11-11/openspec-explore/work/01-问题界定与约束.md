# 01 问题界定与约束

> 探索阶段中间产物。用于对齐「到底在造什么」，不追求完整方案。

## 1. 一句话重述

不是「再写一个 Vue3 后台模板」，而是：**一个可被业务项目 import 的管理后台运行时基座**，把布局、路由、菜单、权限、微前端装配这些重复工作收敛掉，业务方只写页面和配置。

关键词是「运行时」和「被复用」——这两点决定了它必须是一个库，而不是一个复制粘贴的脚手架。

## 2. 真实目标（按优先级）

| 优先级 | 目标 | 可验证的判据 |
| --- | --- | --- |
| P0 | 新业务项目 30~50 行完成初始化即可跑起来 | 从 `pnpm create` 到登录后看到首个页面 < 30 分钟 |
| P0 | 权限（菜单/路由/按钮）开箱可用 | 业务方只提供权限码来源，不写守卫逻辑 |
| P1 | 可选的微前端装配能力 | 不启用时零成本；启用时只加一段配置 |
| P1 | 跟随框架升级不痛苦 | 升级只改版本号 + 跑一条 codemod 命令 |
| P2 | 多团队并行开发同一后台 | 子应用可独立仓库、独立发布 |

## 3. 三个必须区分的东西

很多「后台框架」失败，是因为把下面三件事混成了一个包：

```
+---------------------+  +---------------------+  +---------------------+
|  A. 运行时基座      |  |  B. 页面/业务模板   |  |  C. 工程脚手架      |
|  (npm 库，可升级)   |  |  (代码生成物)       |  |  (CLI，一次性)      |
+---------------------+  +---------------------+  +---------------------+
| 布局/路由/守卫/权限 |  | 用户管理 CRUD 页面  |  | 目录结构/构建配置   |
| 主题/页签/微前端    |  | 订单列表、报表      |  | lint/tsconfig/CI    |
+---------------------+  +---------------------+  +---------------------+
        ^                          ^                        ^
        |                          |                        |
     版本可升级              业务自己维护             生成后可改，不再升级
```

判断标准：
- 需要「跨项目保持一致且能修 bug」的 → A，做成包。
- 每个项目都要改、天然不同 → B，用 CLI 生成到项目里。
- 只影响首次搭建 → C，生成完就脱离框架。

**结论：A 是本次项目的主体；B/C 由 CLI 生成，不做成运行时依赖。** 否则会出现「框架越升级，业务越不敢升」的经典死局。

## 4. 使用场景（用来校验设计）

### 场景 1：单团队新项目（最常见）
一个 Vue3 项目，5 个页面，不需要微前端。
→ 只装 `@admin/core` + `@admin/ui` + `@admin/auth`，不装 `@admin/micro`。

### 场景 2：老系统渐进迁移
存量 Vue2/jQuery 页面按模块迁入，新旧页面共存。
→ 基座 + wujie 子应用，按路径前缀挂载老应用，逐个替换。

### 场景 3：多团队共建
权限中心、订单中心、数据大屏由不同团队维护，发布节奏不同。
→ 基座 + 多个子应用 + 统一权限与菜单。

### 场景 4：框架自身演进
框架修了一个路由守卫的 bug，10 个业务项目要一起受益。
→ 必须是包，且业务侧无可复制的守卫代码。

## 5. 约束（已确认）

- monorepo 组织，Vue3 技术栈。
- 业务项目通过 import 框架包 + 少量初始化获得骨架。
- 必须具备权限配置能力（菜单/路由/按钮，粒度待定）。
- 必须具备微前端能力（形态待定）。
- 已有 git 仓库；OpenSpec 已初始化但无任何 spec/change。

## 6. 非目标（v1 明确不做）

- 不做低代码/可视化搭建。
- 不做后端服务、不做权限管理的管理端（只定义契约）。
- 不做 SSR。
- 不做移动端/H5 适配（除非决策项 Q8 改变）。
- 不追求「零配置支持任意技术栈子应用」；v1 只保证 Vue3 子应用体验，其他技术栈走 iframe 降级。

## 7. 关键假设（已于 2026-11-12 确认，见 `outputs/决策记录.md`）

| 编号 | 假设 | 若不成立的影响 |
| --- | --- | --- |
| A1 | 主要场景是 PC 管理后台 | 布局、组件、交互全部要重做 |
| A2 | 子应用以 Vue3 + Vite 为主 | 适配器选型改变（qiankun 可排除） |
| A3 | 部署同域（不同路径），非独立域名 | token/cookie 传递、跨域隔离方案改变 |
| A4 | 菜单以代码静态定义为主，后端只给权限码 | 需要额外的动态菜单协议与组件白名单 |
| A5 | 至少有两个真实业务项目会复用 | 否则应退化为模板，不该做框架 |

> A5 是最重要的假设。只有一个消费方时，抽象一定错；框架的价值来自「第二次复用时的边际成本」。

## 8. 成功的反面（反模式清单）

1. **抽象泄漏**：`createAdminApp` 的 options 里出现 `wujie`、`element-plus` 的具体类型。
2. **双份清单**：路由写一遍、菜单配置再写一遍，最后不一致。
3. **权限写在页面里**：每个项目自己写 `router.beforeEach`。
4. **子应用接管 URL**：基座失去对地址栏的控制，刷新即 404。
5. **样式全域污染**：子应用一个 `.title` 把基座标题改了。
6. **升级即重构**：框架 1.x → 2.x 需要业务改 200 行。
