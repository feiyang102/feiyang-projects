## 1. 设计原则

1. **契约优先**：`core` 只定义接口与编排，不实现 UI、不实现沙箱。
2. **默认极简**：不用权限就 `auth: false`，不用微前端就不装 `@admin/micro`。
3. **单一事实来源**：路由即清单，菜单/页签/面包屑/权限/缓存全部派生。
4. **基座持有 URL 主权**：任何子应用都不能接管顶层地址栏。
5. **逃生舱**：布局组件可覆盖、路由可裸传、可只使用 `@admin/auth` 不使用 UI。
6. **加性演进**：公共 API 只增不改；破坏性变更必须配 codemod。

## 3. 启动时序

```
业务 main.ts
   |
   v
createAdminApp(options)
   |
   +-- 1. normalizeOptions()      迁移 + 校验 + 默认值 + 废弃告警
   +-- 2. createPinia / createRouter / createHttp（i18n 仅保留配置位置）
   +-- 3. auth.load()             拉取 me，并发去重；失败进入错误态
   +-- 4. buildAccessRoutes()     过滤 + 裁剪空目录 + 排序
   +-- 5. registerModules()       依次执行 module.setup(ctx)
   +-- 6. installGuards()         beforeEach / afterEach / onError
   +-- 7. installGlobals()        v-perm、<Permission>、全局组件
   +-- 8. mount(Layout)           渲染布局与首个路由
   +-- 9. hooks.onReady()
```

时序约束：
- `auth.load()` 必须在首个路由解析前完成，否则会闪 403。
- `module.setup` 在守卫安装前执行，保证模块注册的 store 可用。
- `app.mount` 是 Promise，业务方可 await 后做埋点。

失败分支：

| 失败点 | 行为 |
| --- | --- |
| 配置校验失败 | 开发环境抛错并打印字段路径；生产环境降级为默认值并上报 |
| `me` 401 | 跳登录，带 `redirect` |
| `me` 网络错误 | 渲染错误页 + 重试，不跳登录 |
| 模块 setup 抛错 | 捕获并标记该模块不可用，其余模块继续 |
| 子应用加载失败 | 容器内错误态 + 重试 |

## 4. 路由、菜单、页签数据流

```
defineModule(routes)
        |
        v
+-------------------+      +-------------------+
| 静态路由树        |      | 权限码集合        |
| (代码)            |      | (后端 me)         |
+---------+---------+      +---------+---------+
          |                          |
          +------------+-------------+
                       v
              +------------------+
              | filterRoutes()   |  无权限节点移除；空目录剪枝；menu:false 保留路由但不进菜单
              +--------+---------+
                       |
        +--------------+--------------+--------------+
        v              v              v              v
   +---------+   +----------+   +----------+   +-----------+
   | 侧边菜单 |   | 面包屑   |   | 页签     |   | keep-alive |
   +---------+   +----------+   +----------+   +-----------+
```

派生规则：
- 菜单项 = 路由树中有权限且 `menu !== false` 的节点。
- 页签 = 已访问路由，`affix: true` 常驻；标题取 `meta.title`。
- keep-alive 名单 = `meta.cache === true` 且已访问的路由名。
- 面包屑 = 当前匹配链上 `meta.title` 的数组。
- 详情页通过 `meta.activeMenu` 指定高亮菜单。

### 4.1 静态菜单 + 接口菜单合并

菜单支持两个来源，但**路由骨架永远来自代码**，接口只能覆盖展示信息。

```
静态路由树（代码）
      +
接口菜单数据（可选）        -> mergeMenuOverrides()
      |                           按 key 匹配
      |                           可覆盖 title / icon / order / hidden
      |                           未知 key 忽略（开发环境告警）
      v
  权限过滤（同一套权限码）
      |
      v
  侧边菜单 / 面包屑 / 页签
```

三条硬规则：

1. **接口不能新增页面**。接口下发的 key 必须命中代码里已注册的路由，组件由 `import()` 白名单决定，不由接口指定路径。否则打包器找不到组件，也存在安全风险。
2. **接口失败回退静态菜单**。拉取失败或超时（默认 3s）时使用代码里的静态配置，后台必须可用，不能因菜单接口挂掉而整体不可用。
3. **权限过滤在合并之后**。两个来源共用同一套权限码，不产生第二套判断逻辑。

接口形态（默认按「覆盖项」设计，完整菜单树下发不作为当前范围）：

```ts
GET /api/menus/overrides
200 {
  "items": [
    { "key": "system.user", "title": "账号管理", "icon": "User", "order": 1, "hidden": false }
  ]
}
```

> 若后续需要「运营完全自定义菜单树」，属于扩展项，见 [能力扩展规划](./能力扩展规划.md)。届时仍需保留 key 白名单校验。

为什么不做独立菜单配置：一旦菜单与路由彻底分开，就会出现「有菜单无路由」「路由改名菜单没改」「权限过滤两套逻辑」三类 bug，且无法静态校验。

## 5. 微前端运行时

### 5.1 适配器接口（core 只认识这个）

```ts
export interface MicroAppAdapter {
  readonly name: string
  mount(
    container: HTMLElement,
    app: MicroAppDefinition,
    ctx: MicroHostContext,
  ): Promise<MicroAppInstance>
}

export interface MicroAppInstance {
  readonly name: string
  update(props: Record<string, unknown>): void
  destroy(): Promise<void>
}

export interface MicroHostContext {
  router: Router
  bridge: Bridge
  getProps(): Record<string, unknown>
  reportRouteChange(payload: RemoteRouteInfo): void
  reportError(error: unknown): void
}
```

内置适配器：
| 适配器 | 依赖 | 用途 |
| --- | --- | --- |
| `wujie` | wujie（可选 peer） | 当前主实现，Vue3/Vite 子应用 |
| `iframe` | 无 | 零依赖降级，用于 wujie 不可用或极简场景 |

> Module Federation 适配器不在当前范围，接口保留即可，见 [能力扩展规划 · L4](./能力扩展规划.md)。

### 5.2 挂载组件

```vue
<!-- @admin/micro 提供，业务方不直接写 -->
<MicroAppHost
  :name="route.meta.micro"
  :definition="registry.get(route.meta.micro)"
  @route-change="onRemoteRouteChange"
  @error="onRemoteError"
/>
```

`MicroAppHost` 职责：
- 首次进入时 `adapter.mount`，离开时按 `alive` 策略 `destroy` 或保留。
- 路由参数变化时不重新 mount（容器 key 固定为子应用名）。
- 加载态、超时（默认 10s）、错误态、重试。
- 通过 `props` 注入上下文快照。
- 监听 bridge 事件并转成宿主回调。

### 5.3 路由模式与 URL 归属

**delegated（默认）**

```
URL: /order/detail/1001
      |___________________|
         子应用内部路由（base = /order）

基座路由：{ path: '/order/:pathMatch(.*)*', component: MicroAppHost, meta: { micro: 'order' } }
```

- 子应用使用 `createWebHistory('/order')`，独立运行时同样可用。
- `sync = false`，不启用 wujie 的 URL 同步，避免双路由互相 push。
- 两个 router 同时监听 history：基座只匹配 catch-all，不主动 push 子应用路径；子应用 push 后基座仅更新参数，不重挂容器。
- 深链刷新：基座 catch-all 命中 → 挂载子应用 → 子应用按 base 解析当前路径。

> 风险：两个 router 同时监听 popstate。M3 必须先做一个 spike 验证前进/后退、同路径重复 push、query 变化三种情况。若不稳定，切换到「子应用 memory history + 基座显式路径映射」方案。

**autonomous（存量迁移）**

```
基座路由：{ path: '/legacy/:pathMatch(.*)*', meta: { micro: 'legacy', chrome: false } }
```

- 子应用完全自治，基座只提供外壳或全屏容器。
- 不参与页签、面包屑、按钮权限。

### 5.4 生命周期映射（wujie）

| 基座事件 | wujie 调用 | 说明 |
| --- | --- | --- |
| 首次进入 | `setupApp` + `startApp({ el })` | 传入 props 快照 |
| 主题变化 | `instance.update({ theme })` 或 bus | 优先 CSS 变量，减少通信 |
| 权限变化 | bus `host:auth-change` | 子应用自行刷新按钮态 |
| 切走（alive） | 隐藏容器 | 保留子应用状态 |
| 销毁 | `destroyApp(name)` | 登出/切换用户时强制销毁 |
| 子应用路由变化 | props 回调 / bus `app:route-change` | 更新面包屑与页签标题 |
| 子应用异常 | `app:error` | 基座错误边界接管 |

### 5.5 通信契约（`@admin/bridge`）

```ts
interface BridgeEvents {
  'host:theme-change': ThemeTokens
  'host:auth-change': AuthSnapshot
  'host:locale-change': string
  'app:route-change': { app: string; path: string; title?: string; breadcrumb?: string[] }
  'app:error': { app: string; message: string; stack?: string }
  'app:request-auth': { reason: string }
}

interface Bridge {
  emit<K extends keyof BridgeEvents>(event: K, payload: BridgeEvents[K]): void
  on<K extends keyof BridgeEvents>(event: K, handler: (p: BridgeEvents[K]) => void): () => void
  request<T>(method: string, params?: unknown): Promise<T>
  provide(method: string, handler: (params: unknown) => Promise<unknown>): void
}
```

约束：
- 只传可序列化快照，不传 Vue 响应式对象、router 实例、pinia 实例。
- `request` 用于基座能力代理（刷新 token、打开全局弹窗、获取用户信息），避免子应用直连基座内部。
- 事件名集中定义，禁止字符串散落。

### 5.6 隔离边界

| 资源 | 策略 |
| --- | --- |
| JS 全局 | iframe 独立 realm（wujie） |
| CSS | Shadow DOM；主题只通过 CSS 变量 |
| 路由 | 基座持 URL，子应用挂载在容器内 |
| 状态 | 不共享 pinia；通过 props/bridge 传快照 |
| 网络 | 子应用用自己的 http 实例；401 通过 bridge 上报基座统一处理 |
| 存储 | localStorage 同域共享，约定 key 前缀；敏感信息不进 localStorage |
| 定时器/事件 | 子应用卸载时自行清理；基座在 destroy 时兜底 |

### 5.7 安全与白名单

- 子应用 `entry` 必须来自构建期配置或后端下发的白名单，禁止 URL 参数直接指定。
- 仅允许 `http/https`，禁止 `javascript:`、`data:`。
- 跨域子应用需配置 `Access-Control-Allow-Origin`，并在基座侧声明允许的 origin。
- 子应用不应能读取宿主 token（同域 Cookie 除外）；跨域时使用短期 token + bridge 代理。

## 6. 权限实现要点

### 6.1 匹配器（纯函数，易测）

```ts
function matchPermission(granted: string[], required: string): boolean {
  if (granted.includes('*')) return true
  if (granted.includes(required)) return true
  const [domain, resource] = required.split(':')
  return granted.includes(`${domain}:${resource}:*`)
}
```

### 6.2 守卫顺序

```
1. 白名单路由（/login, /403, /404）直接放行
2. 无 token -> /login?redirect=
3. 未加载 me -> await auth.load()（promise 去重）
4. me 失败 -> /error（可重试），不跳登录
5. 路由不存在 -> /404
6. 路由存在但无权限 -> /403
7. 通过 -> 记录页签、设置标题
```

### 6.3 指令与组件

```ts
// v-perm 支持修饰符
v-perm="'system:user:create'"          // 无权限移除节点
v-perm.disable="'system:user:create'"  // 无权限置灰
v-perm.any="['a','b']"                 // 任一命中
v-perm.all="['a','b']"                 // 全部命中
```

### 6.4 缓存与刷新

- `me` 结果存内存 + `sessionStorage`，带 `permissionsVersion`。
- 任意接口返回 403：触发一次 `me` 刷新；版本变化则重建路由与菜单。
- 登出/切换用户：清空 store、页签、keep-alive、子应用实例。
- 多标签页：`storage` 事件同步登出。

## 7. 配置、兼容与升级

### 7.1 配置校验

```ts
function normalizeOptions(raw: unknown): AdminAppOptions {
  const migrated = runMigrations(raw)       // 按 configVersion 逐版本迁移
  const parsed = optionsSchema.parse(migrated) // zod
  warnDeprecated(migrated)                  // 每个废弃字段只告警一次
  return applyDefaults(parsed)
}
```

规则：
- `configVersion` 必填；缺失时按 1 处理并告警。
- 废弃字段保留至少一个大版本，迁移期打印替代写法。
- 未知字段：开发环境告警，生产环境忽略（避免阻断上线）。

### 7.2 版本策略

| 阶段 | 版本 | 说明 |
| --- | --- | --- |
| M0~M5 | `0.x` | 快速演进，允许 breaking，每次在 CHANGELOG 写明迁移点 |
| 有第二个真实消费方后 | `1.0` | 冻结公共 API，进入 semver |
| 之后 | `1.x` 加性 | breaking 必须走 `2.0` + codemod |

- M5 引入 changesets `fixed` 组，保证运行时包同版本。
- `@admin/cli` 独立版本，但要声明兼容的 core 范围。

### 7.3 升级路径

**当前范围只做到「升级可诊断」**：

```
业务项目升级：
  1. 改 package.json 版本（固定组一起改）
  2. 启动时若 configVersion 缺失或落后，控制台给出精确迁移提示
  3. CHANGELOG 列出：新增 / 废弃 / 破坏
```

**后期再做「升级可自动」**：`@admin/cli upgrade` 用 codemod 改配置与 API（options 重命名、`defineModule` 签名、指令/组件 API、导入路径）。属于扩展项，不阻塞当前开发。

## 8. 构建与发布链路

```
pnpm workspace
  packages/*        -> tsup 构建 ESM + d.ts
  examples/*        -> vite 构建
  |
  v
turbo run build lint typecheck test
  |
  +--> api-extractor 生成公共 API 报告（PR diff 检查，M1 起）
  +--> size-limit 检查各入口体积（可选）
  +--> changesets 生成版本与 CHANGELOG（M5）
  +--> 发布：先 `pnpm pack` + 本地 tarball 验证，公共/私有 registry 待定
```

包配置要点：

```json
{
  "type": "module",
  "sideEffects": ["**/*.css"],
  "exports": {
    ".": { "types": "./dist/index.d.ts", "import": "./dist/index.js" },
    "./style.css": "./dist/style.css",
    "./adapters/wujie": "./dist/adapters/wujie.js"
  },
  "peerDependencies": {
    "vue": "^3.4.0",
    "vue-router": "^4.3.0",
    "pinia": "^2.1.0 || ^3.0.0"
  }
}
```

- 不打包 `vue` / `vue-router` / `pinia`，避免多实例。
- UI 库（如 element-plus）作为可选 peer，由 `@admin/ui` 的适配层引用。
- CSS 单独产出，业务方显式引入，避免样式副作用。
- 子路径导出隔离重依赖：`@admin/micro/adapters/wujie` 才引入 wujie。

## 10. 当前开发路线（M0–M5）

| 阶段 | 交付 | 完成标志 |
| --- | --- | --- |
| M0 | pnpm workspace + 包骨架 + 构建链路 | `pnpm build` 通过，demo 能引用本地包 |
| M1 | core + ui + auth：登录、静态路由、菜单、按钮权限、页签 | 假数据后台能登录并切换页面 |
| M2 | 接口菜单覆盖 + 权限过滤 + 失败回退 | 改接口数据能改变菜单；接口挂掉仍可用 |
| M3 | micro + wujie + bridge：基座挂载子应用、子应用独立运行 | `/order/*` 深链刷新正常；子应用崩溃有兜底 |
| M4 | CLI 生成 shell / sub-app 模板 | 新目录 5 分钟内跑起来 |
| M5 | 发布准备：exports、changesets、`pnpm pack` 验证 | 外部工程能安装本地 tarball 并运行 |

顺序理由：
- M3 是微前端学习重点，但必须在 M1/M2 的基座跑通之后，否则没有可挂载的壳。
- M4 放最后，避免过早把错误设计固化成模板。
- M5 先做到「能被外部工程安装」，是否发公共 npm 待定。

每个阶段结束更新 `examples/playground`，它是框架契约的活文档。
