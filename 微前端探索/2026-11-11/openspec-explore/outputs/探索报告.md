## 0. 结论先行

**把它做成「可升级的运行时基座 + 可选微前端插件」，而不是一个后台模板。**

业务项目只写页面与配置；布局、路由、菜单、页签、权限、微前端装配由包提供。微前端不是地基，而是按需安装的一层装配能力。

### 五个关键判断

| # | 判断 | 理由 |
| --- | --- | --- |
| 1 | 库，不是模板 | 模板无法跨项目修 bug；框架的价值在第二次复用时才体现 |
| 2 | 微前端是插件，不是 core | 不用微前端的项目应零成本；`core` 依赖 `wujie` 会导致抽象泄漏与包体积浪费 |
| 3 | 路由即清单（route-as-manifest） | 菜单、面包屑、页签、权限、缓存全部从路由派生，消灭双份配置 |
| 4 | 基座持有 URL 主权 | 子应用接管顶层路由会导致刷新 404、页签错乱、面包屑失效 |
| 5 | 权限前端只做 UX，后端是唯一权威 | 前端权限是展示收敛，不是安全边界；前端只消费后端计算好的扁平权限码 |

## 1. 问题空间

### 三类使用者

```
+------------------+      +------------------+      +------------------+
| 框架维护者       |      | 业务开发者       |      | 子应用团队       |
+------------------+      +------------------+      +------------------+
| 保证多项目一致   |      | 只想写页面       |      | 独立开发/发布    |
| 修一次全员受益   |      | 不想懂微前端     |      | 不想被基座绑架   |
| 敢发 breaking    |      | 怕升级破坏业务   |      | 要能独立运行     |
+------------------+      +------------------+      +------------------+
```

三者的诉求互相拉扯：维护者想统一，业务方想自由，子应用团队想解耦。方案必须在三者之间给出明确的「可替换边界」。

### 三种典型失败

1. **模板化失败**：每个项目复制一份，修 bug 要改 N 个仓库，最后版本分裂。
2. **过度框架化失败**：什么都想管，业务方每做一个需求就要给框架提 PR，最后被绕过。
3. **微前端先行失败**：为了「架构先进」引入微前端，结果团队只有 3 个人，多出沙箱、通信、部署三套复杂度。

## 2. 微前端形态：结论与依据

完整对比见 [02-微前端形态对比](../work/02-微前端形态对比.md)。

| 方案 | 适合 | 不适合 |
| --- | --- | --- |
| qiankun | 存量 webpack 项目、强生态依赖 | Vite/ESM、UI 库弹层多的后台 |
| **wujie** | Vue3 + Vite、需要强隔离、UI 库弹层多 | 追求极致性能、需要源码级调试 |
| micro-app | 轻量接入、CustomElement 体系 | 对第三方 UI 库样式隔离要求极高 |
| Module Federation 2.0 | 同栈共享页面/组件/依赖 | 异构技术栈、独立部署的整站子应用 |
| 纯 npm 包 | 同团队、同发布节奏 | 需要独立部署与运行时组合 |

**推荐**：`@admin/micro` 默认 wujie 适配器；保留 iframe 降级与 MF 适配器接口；`core` 只认识 `MicroAppAdapter` 接口。

选择 wujie 的决定性理由：
- iframe 原生 JS 隔离，子应用几乎零改造。
- 子应用的 Dialog/Popper 在自己的 document 内渲染，不会逃逸到宿主导致样式错乱——这是管理后台的高频痛点。
- Shadow DOM 隔离样式，同时 CSS 变量可继承，主题令牌天然穿透。
- 原生支持 Vite/ESM。

代价：
- iframe 内调试体验一般，内存开销略高。
- 社区规模小于 qiankun，需要自己兜底升级风险。

## 3. 推荐架构

```
+---------------------------------------------------------------+
|                        业务项目（消费者）                      |
|  main.ts：createAdminApp({...})  ~30 行                         |
|  modules/：页面 + defineModule()                                |
+-------------------------------+-------------------------------+
                                |
        +-----------------------+-----------------------+
        |                       |                       |
+-------v--------+     +--------v--------+     +--------v--------+
|   @admin/ui    |     |   @admin/auth   |     |  @admin/micro   |
| 布局/菜单/页签 |     | 权限引擎/守卫   |     | 适配器/Host     |
| 主题令牌       |     | 指令/组件       |     | wujie/iframe/MF |
+-------+--------+     +--------+--------+     +--------+--------+
        |                       |                       |
        +-----------------------+-----------+-----------+
                                    |
                          +---------v---------+
                          |    @admin/core    |
                          | 应用工厂/路由编排 |
                          | 生命周期/配置校验 |
                          +---------+---------+
                                    |
                    vue / vue-router / pinia (peerDependencies)

+-------------------+        +----------------------------------+
|    @admin/cli     |        |  examples/playground（契约测试） |
| 创建/生成/升级     |        |  examples/remote-order（子应用） |
+-------------------+        +----------------------------------+
```

关键约束：
- `core` 不依赖 UI 库、不依赖微前端库。
- `ui` 不依赖 `auth`（过滤后的菜单由 core 传入）。
- `micro` 把 `wujie` 设为可选 peerDependency。
- 所有运行时包固定同版本发布。

## 4. 对外契约摘要

### 业务项目初始化（目标：50 行以内）

```ts
import { createAdminApp } from '@admin/core'
import { adminPreset } from '@admin/ui'
import { createHttpAuth } from '@admin/auth'
import systemModule from './modules/system'
import '@admin/ui/style.css'

createAdminApp({
  configVersion: 1,
  app: { name: 'console', title: '运营管理后台' },
  auth: createHttpAuth({ loginUrl: '/api/auth/login', meUrl: '/api/auth/me' }),
  layout: adminPreset({ tabs: true, breadcrumb: true }),
  modules: [systemModule],
}).mount('#app')
```

### 模块协议

```ts
export default defineModule({
  name: 'system',
  routes: [
    {
      path: '/system/user',
      component: () => import('./views/UserList.vue'),
      meta: { title: '用户管理', permission: 'system:user:list', cache: true },
    },
  ],
  setup(ctx) { /* 注册 store / 全局组件 */ },
})
```

### 微前端定义（仅在使用时引入）

```ts
defineMicroApp({
  name: 'order',
  entry: '//order.example.com',
  basePath: '/order',
  mode: 'delegated',
  adapter: 'wujie',
  permission: 'order:view',
  props: (ctx) => ({ token: ctx.auth.token, theme: ctx.theme.tokens }),
})
```

完整契约见 [方案设计 · 第 5 节](./方案设计.md)。

## 5. 权限模型摘要

```
后端 GET /auth/me
  { user, roles, permissions: ["system:user:list", ...], permissionsVersion }
        |
        v
+------------------+     +------------------+     +------------------+
| 路由过滤         | --> | 菜单 / 面包屑    | --> | 页签 / keep-alive|
+------------------+     +------------------+     +------------------+
        |
        +--> 按钮：v-perm / <Permission> / useAuth().can()
```

- 权限码格式 `<domain>:<resource>:<action>`，支持 `*` 与 `domain:resource:*`。
- 后端返回「有效权限全集」，前端不做角色→权限展开（避免双份真相）。
- 菜单由路由派生，不提供独立菜单配置。
- 前端权限不构成安全边界，所有接口后端必须独立鉴权。
- 数据级权限 v1 不做，仅预留字段。

## 6. 接入成本与升级路径

### 接入成本

| 项目类型 | 需要做的事 |
| --- | --- |
| 普通新后台 | 装 3 个包 + 写 30 行 + 按 `defineModule` 写页面 |
| 需要微前端 | 多装 `@admin/micro` + wujie，多写 1 个 `defineMicroApp` |
| 存量系统迁移 | 子应用保持原样，基座加一条 autonomous 路由 |

### 升级路径

1. `configVersion` 必填，运行时按版本迁移配置并打印废弃告警。
2. `@admin/cli` 提供 `admin upgrade`，用 codemod 处理 API 重命名。
3. 运行时包固定版本组，避免「core 2.1 + ui 1.9」的错配。
4. `examples/playground` 始终跟随最新版，作为契约回归。
5. 公共 API 用 api-extractor 快照，意外 breaking 在 CI 就被拦截。

## 7. 风险登记

| 风险 | 概率 | 影响 | 缓解 |
| --- | --- | --- | --- |
| 只有 1 个消费方就做抽象，抽象必然错 | 高 | 高 | 先用 playground + 1 个真实项目跑通，第二次复用时再冻结 API |
| 微前端实际不需要，复杂度白白增加 | 中 | 中 | 明确为学习目的，只做最小闭环；默认不启用 |
| UI 库类型泄漏到公共 API | 中 | 中 | 公共 API 只用自有类型；UI 库通过适配层隔离 |
| 路由与子应用双重接管导致刷新 404 | 中 | 高 | 基座持有 URL；子应用只挂载在容器 |
| 主题/样式隔离不彻底 | 中 | 中 | 只以 CSS 变量作为跨应用样式契约 |
| 权限变更后前端缓存不一致 | 中 | 中 | `permissionsVersion` + 403 时强制刷新 |
| 升级 breaking 导致业务不敢升 | 中 | 高 | codemod + 契约测试 + 固定版本组 |
| 包体积/重复 Vue 实例 | 低 | 中 | peerDependencies + 外部化 vue/vue-router/pinia |

## 8. 当前开发路线（M0–M5）

| 阶段 | 内容 | 退出标准 |
| --- | --- | --- |
| M0 | pnpm workspace + 包骨架 + 构建链路 | `pnpm build` 通过，demo 能引用本地包 |
| M1 | core + ui + auth：登录、静态路由、菜单、按钮权限、页签 | 假数据后台能登录并切换页面 |
| M2 | 接口菜单覆盖 + 权限过滤 + 失败回退 | 改接口数据能改变菜单；接口挂掉仍可用 |
| M3 | micro + wujie + bridge：基座挂载子应用、子应用独立运行 | `/order/*` 深链刷新正常；子应用崩溃有兜底 |
| M4 | CLI 生成 shell / sub-app 模板 | 新目录 5 分钟内跑起来 |
| M5 | 发布准备：exports、changesets、`pnpm pack` 验证 | 外部工程能安装本地 tarball 并运行 |

**建议**：M3 依赖 M1/M2 的壳先跑通；M4 必须等契约稳定后再做，避免把错误设计固化成模板。
